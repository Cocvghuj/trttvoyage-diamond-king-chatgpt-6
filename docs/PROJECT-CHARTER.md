# TRTT Voyage — Diamond King Project Charter

**Vision:** TRTT Voyage — From Vision to Global Brand. Explore Beyond. Discover Everything.  
**Team principle:** One Team. One Vision. One Journey.

## Purpose
This repository is the public-safe command-center handbook for the TRTT Voyage / Diamond King collaboration. It documents reusable principles, workflows, project architecture, and contribution standards. It is not a storage location for credentials, private user data, or confidential operational records.

## Core values
1. Truth before profit.
2. Evidence before publication.
3. Security before automation.
4. Quality before speed.
5. Preserve history; make changes additively.
6. Report uncertainty and unverified work honestly.

## Scope
- Public-safe project guidance and reusable operating procedures.
- Documentation for Blog, GitHub, GitLab, ChatGPT workflows, and SaaS/tool development.
- Templates for change records, daily logs, testing evidence, and release notes.
- High-level architecture and quality gates.

## Out of scope
- Passwords, API tokens, private keys, passphrases, recovery codes, or session cookies.
- Personal contact details or private family/health information.
- Unverified analytics, fabricated tests, invented URLs, or claims of deployment.
- Direct production publishing, Main-branch merges, DNS changes, or security/permission changes without explicit approval.

## Change policy
- Prefer feature branches and pull requests.
- Never delete or overwrite historical records as a routine update.
- Add a new dated record or a new version when preserving history matters.
- Inspect before editing; verify after every write.
- A successful file write is not proof that the application works.

## Status vocabulary
- **PASS** — directly verified with evidence.
- **FAIL** — a check ran and failed.
- **NOT TESTED** — no test was run.
- **BLOCKED** — a dependency prevents progress.
- **WAITING FOR APPROVAL** — a protected action needs the owner's explicit approval.

## Release gate
A deliverable is ready only when its scope, changed files, validation steps, known limitations, and rollback/restore approach are documented. Never describe a draft as published or a static review as a successful runtime test.
