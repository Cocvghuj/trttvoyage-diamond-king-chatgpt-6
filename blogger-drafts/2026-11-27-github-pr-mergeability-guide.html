How to Handle a GitHub Pull Request That Cannot Be Merged

A practical guide to diagnosing mergeability without risking project history.

A GitHub pull request (PR) can be ready for review but still show that it cannot be merged. That status should trigger a careful diagnosis, not an automatic force-push or an assumption that a conflict exists.

1. Read the current PR state first

Confirm the repository, source branch, target branch, latest commit and current PR state. An older screenshot or copied status may no longer describe the live request. Check the current GitHub page and its latest checks and review activity.

2. Do not confuse every blocker with a conflict

A merge conflict is only one possible reason a PR cannot be merged. Required checks may be failing or pending. A review may still be required. Repository rules may prevent merging. GitHub may also report that mergeability has not yet been calculated.

An API value of mergeable=false alone is not enough to claim that a specific file conflict has been found. Inspect the merge state and supporting evidence before naming the cause.

3. Protect the original work

Before proposing a resolution, compare the PR with the latest target branch and inspect every affected file. Preserve unrelated changes, existing content, project memory and commit history. Do not force-push, delete branches, dismiss reviews or bypass required checks as a routine shortcut.

4. Match the next action to the evidence

  • Confirmed conflict: prepare a reviewable resolution and explain affected files.
  • Failing check: inspect the failed job and correct only the relevant cause.
  • Pending review: wait for the required reviewer or Owner decision.
  • Policy restriction: report the exact rule without weakening protection.
  • Unknown state: refresh the status instead of guessing.

5. Make the handoff evidence-based

A useful report includes the PR link, source and target branches, latest head commit, exact mergeability result, checks and review status, confirmed blocker, and the next safe action. Clearly label anything that has not been tested or verified.

Frequently asked questions

Does “not mergeable” always mean there is a code conflict?

No. It can reflect checks, reviews, repository rules or an unresolved mergeability calculation. Confirm the reason before acting.

Should an assistant force-push a fix automatically?

No. History rewriting can affect other contributors and should never be treated as an automatic repair. Preserve the original branch and obtain Owner approval for protected history operations.

Can a PR be merged as soon as conflicts are resolved?

Not necessarily. Required checks, reviews and repository policies still apply, and the Owner controls the merge decision.

Does merging prove the production website changed?

No. Merge, deployment and live-site verification are separate events and require separate evidence.
